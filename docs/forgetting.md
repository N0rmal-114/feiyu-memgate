# 遗忘曲线（用户文档）

这份文档讲怎么用：打开、配置、日常命令、备份、写自己的曲线、限制。设计的来龙去脉在 [遗忘曲线设计](design/2026-11-14-forgetting-curve.md)，模拟结果在 `bench/results/forgetting/summary.md`。

## 它做什么，不做什么

做的事：

- 给每条记忆记三个时间和一个次数：记忆自己的日期、账本第一次知道它的时间（开始被管理）、最近一次被用到的时间，以及“用到的次数”。“用到”怎么算见下面的“用到怎么算”：召回时只给最相关的那几条记一次，客户端也可以用 `POST /v1/used` 明说“这几条我真的用了”。
- 召回时按保持率给分数乘一个**有界**的系数：`floor + (1 - floor) × R`，`floor` 默认 0.7。很久没被用到的记忆最多损失 30% 的分数：相关性说了算，新旧只是决定“差不多相关”的几条谁先谁后。这由召回阶段 `freshness` 完成。
- 定时（或手动）清理：在被管理的状态下，整整一个曲线寿命（默认约 389 天）没有被用到的记忆，先把全文写进存档，再从存储里删除。存档默认保留 90 天，期间可以恢复，过期后真正删掉。
- 限速：每次清理、每个存储最多忘 `max(max_forget_min, max_forget_fraction × 该存储条数)` 条（默认 `max(5, 2%)`），先忘保持率最低的，其余留到后面的清理（报告里的 `held`）。同一天到期的一批记忆因此是分几天忘掉的，时钟错了、半衰期设错了，一次清理最多损失一小片，而且是存了档、可以恢复的。
- 钉住的记忆（手动钉住、匹配地址规则、写入时钉住）排序时不打折、永不遗忘。**身份类信息要钉住**（见“钉住”）：不钉住的话，它们和别的记忆一样，一个曲线寿命没被用到就会被忘。

不做的事：

- 不配置 `[forgetting]` 时，这个功能完全不存在，现有行为不变。
- HTTP 接口里没有删除。删除只由清理任务做（网关里的定时任务，或主机上的 `forget sweep`）。`POST /v1/used` 只能刷新一条记忆的“最近用到”和次数，不能删、不能改、不能读出内容。
- 只管 `[forgetting].stores` 里列出的存储，其他存储一条都不碰。
- 账本里不放记忆内容；清理和命令的输出里也不放（除非你给 `forget archive` 加 `--show-text`）。
- 不调用任何模型。

## 打开它

在配置文件里加一节 `[forgetting]`，并把 `freshness` 放进召回阶段：

```toml
[stores.private]
type = "sqlite"
path = "data/private.db"

[clients.owner]
token_env = "GATEWAY_TOKEN_OWNER"
recall = ["private"]
write = "private"
pin_writes = true                 # 这个客户端写入的记忆自动钉住（见下）

[recall]
stages = [
    { type = "min_score", value = 0.3 },
    { type = "freshness", floor = 0.7, credit = "top" },     # 放在 min_score 后面
    "drop_marker", "redact", "dedupe", "budget",
]

[forgetting]
ledger = "data/ledger.db"         # 账本：地址、时间、次数，不含正文
archive = "data/forgotten.db"     # 存档：含记忆全文
stores = ["private"]              # 共享存储的名字，或租户提供方的名字
demote_below = 0.3                # 保持率低于它：降权
forget_below = 0.05               # 保持率低于它：到期，下次清理时存档并删除
archive_days = 90                 # 存档保留多少天
sweep_every_hours = 24            # 网关每隔多少小时自动清理一次；0 = 只手动
pin_refs = ["*/profile.md"]       # 地址匹配这些通配符的记忆永远不忘
max_forget_fraction = 0.02        # 限速：每次清理、每个存储最多忘 max(max_forget_min, 这个比例 × 条数) 条
max_forget_min = 5                # 限速的下限：小存储每次也可以忘这么多条

[forgetting.curve]
type = "ebbinghaus"               # 曲线是一块拼图，见“写自己的曲线”
half_life_days = 90
per_store = { private = 180, group = 30 }
reinforce = 1.6
max_uses = 8
```

要点：

- `freshness` 要放在 `min_score` 后面，这样分数线只看相似度，新鲜度只影响排序。它可以和 `source_weight` 叠加，合起来是“相似度 × 来源权重 × 新鲜度”，新鲜度在 `floor`（默认 0.7）到 1 之间。没有 `[forgetting]` 却写了 `freshness`，配置会报错。
- 只写了 `[forgetting]` 没写 `freshness`：清理照常进行，但召回不按新旧排序。`feiyu-memgate check` 会提醒。
- `stores` 里的共享存储必须有 `refs`、`delete`、`put` 三个能力，否则配置报错。租户提供方（例如 `directory`、`keyfile`）要能列出租户（有 `list()`），否则清理会跳过它。
- 启动网关后，第一次自动清理在 `sweep_every_hours` 小时之后，不是启动时。
- **在一个已经存了很久的库上打开是安全的：打开当天不会删任何东西。** 老记忆的日期很早，排序里会立刻被打到新鲜度的下限（报告里是“降权”状态），但删除的计时从账本第一次知道它的那一刻开始，整整一个曲线寿命（默认约 389 天）没被用到才可以删；这期间被用到的会重新计时。
- 还是建议先运行 `forget sweep --dry-run` 看一眼。要知道：所有记忆在同一天开始被管理，其中没被用到的会在同一天一起到期；限速让它们分成每次最多 `max(5, 2%×条数)` 条，一天一次清理的话，几十天内忘完（模拟里 183 到 204 条在一个多月内忘完，见 `bench/results/forgetting/summary.md`）。这仍然是**一批记忆被整批忘掉**，只是更慢、每一步都存了档。想先看看会忘哪些，用 `forget sweep --dry-run`；想拦住某一批，先钉住它们，或者把 `max_forget_min` 和 `max_forget_fraction` 都设成 0（只有 `forget sweep --force` 才会删）。
- 在已经有数据的网关上改设置（比如把 `floor` 或 `credit` 改掉）不需要迁移，账本不变。

## 用到怎么算

“用到”决定一条记忆的两个计时什么时候重新开始、半衰期变长一档。被召回不等于有用：如果每条返回的都算用到，一条总是搭车出现在前 5 名里的噪声会被一直“保鲜”，而一条相关但没人问到的记忆照样老去，这是越富越富的循环。所以有两道：

**1. 召回时的计用规则**（`freshness` 阶段的 `credit`）：

| `credit` | 谁记一次“用到” |
|---|---|
| `"top"`（默认） | 返回的条目里相似度最高的那一条（相似度是打折前的分数，`meta["similarity"]`），以及其他相似度不低于它 `credit_ratio`（默认 0.9）倍的条目 |
| `"all"` | 返回的每一条（旧的做法） |
| `"none"` | 召回从不记“用到”（部署里由客户端用 `/v1/used` 明确回报时用） |

只看被管理的存储里返回的条目；只有一条时它就是最高的。

召回步骤 `linked`（默认的一套里在 `freshness` 之后）接上的记忆，交付以后和别的条目一样按这条规则算：`"all"` 全记，`"none"` 不记，`"top"` 看它的相似度，而接上的条目的 `meta["similarity"]` 是它排在后面的那个分数（那条记忆的分数 × 邻居的相似度，不高于第一轮里最低的分数），所以默认的 `"top"` 下通常不记，只有它几乎和最高者一样高（不低于 `credit_ratio` 倍）才记。接上的记忆没有乘新鲜度，也没有 `meta["retention"]`。

**2. 客户端明说**：`POST /v1/used`，聊天程序在回复之后告诉网关“这次回复真正依赖了哪几条”：

```
POST /v1/used   Authorization: Bearer <令牌>
{"used": [{"source": "private", "id": "m-0042"}], "tenant_id": "10001"}   →   {"status": "ok", "recorded": 1}
```

- 鉴权、限流、租户的规则和召回一样；客户端必须能从每个写出的 `source` 召回（租户存储用提供方的名字，和召回结果里的一样）。一次最多 20 项。格式不对是 400 `bad_used`，来源不在客户端能召回的范围里是 403 `forbidden`；完整规则和错误码见 [api.md](api.md#post-v1used)。
- 每一条存在的记忆记一次“用到”：两个计时都重新算、次数加一。网关只回“记下了几条”，不会说某个 id 存不存在；编造的 id 什么也不记。
- 没有配置遗忘时照样回 200，`recorded` 是 0，客户端不用知道。
- 它只能刷新记忆的时钟，不能删除、改写或读出记忆。
- Python 客户端：`MemoryClient.report_used(items, tenant_id=None)`，`items` 可以直接是召回结果里的字典；成功返回 `True`，任何失败返回 `False`，不会抛异常。要“只按回报来记”，把 `credit` 设成 `"none"`。

## 曲线

```
保持率 R = 0.5 ^ ( 年龄（天） / 半衰期 )
半衰期   = 这个来源的基础半衰期 × 巩固系数 ^ min(用过的次数, 次数上限)
```

**每条记忆有两个年龄，对应两个保持率**（账本里有两个起点：`first_seen` 是记忆自己的日期，`managed_since` 是账本第一次知道这条记忆的时间）：

| | 用在哪 | 年龄从哪里算起 | 引擎方法 |
|---|---|---|---|
| 排序用的保持率 | 召回时给分数打折（`freshness`）、“降权”状态 | 最近用到的时间；从没用到过就从记忆自己的日期（没有日期就从账本第一次见到它的时间）算起 | `ranking_retention` |
| 删除用的保持率 | “到期”状态：清理要不要删 | “最近用到”和“开始被管理”里**较晚**的那个 | `deletion_retention` |

所以一条日期很早、没人用的记忆，在排序里排得靠后（对的），但不会因为日期早就被删：它只有在被管理的状态下整整一个曲线寿命没被用到才到期。每用一次，两个年龄都重新从 0 算，半衰期也变长一档。恢复（`forget restore`）把“最近用到”和“开始被管理”都设成现在。账本里还没有这条记忆时，删除计时从“现在”算，不会到期。

两条线：

| 线 | 默认 | 用哪个保持率 | 到线以后 |
|---|---|---|---|
| 降权线 `demote_below` | R < 0.3 | 排序用的 | 只是报告里的状态“降权”：这条记忆的新鲜度快到下限了，以后是被删的候选。**不改变排序**（排序用的是同一个有界公式） |
| 遗忘线 `forget_below` | R < 0.05 | 删除用的 | 到期：下一次清理时存档、删除（受限速限制） |

召回时分数乘以新鲜度，所有状态用同一个有界公式：`新鲜度 = floor + (1 - floor) × R`（`floor` 默认 0.7），钉住的恒为 1。这里的 R 是排序用的。所以新鲜度总在 `floor` 到 1 之间，再旧的记忆也最多损失 30% 的分数：

| 排序保持率 R | 1 | 0.5 | 0.3（降权线） | 0.1 | 0 |
|---|---|---|---|---|---|
| 默认新鲜度（floor 0.7） | 1.00 | 0.85 | 0.79 | 0.73 | 0.70 |

例：一条很久没用的记忆相似度 0.9，得分 0.9 × 0.70 = 0.63；一条刚用过但并不相关的记忆相似度 0.5，得分 0.5 × 1.00 = 0.50。强匹配排在前面。新鲜度只会重排“相似度相差不到 30% 以内”的几条：相似度 0.80 的旧记忆（得分 0.56）输给相似度 0.78 的新记忆（得分 0.78）。（旧版本里降权后没有保底，0.9 的旧记忆会被乘到接近 0，排在不相关的新记忆后面，混合后端上因此热题 Hit@5 掉了 12.5 个百分点。）

下表是“从起点起，再没被用到，过多少天进入“降权”状态（按排序用的年龄；只是报告）、过多少天到期（按删除用的年龄）”，用默认的巩固系数 1.6、次数上限 8、降权线 0.3、遗忘线 0.05 算出（向上取整到天）。对一条从没被用到的记忆，降权的起点是它的日期，到期的起点是开始被管理的那一天：

| 基础半衰期 | 已用次数 | 当前半衰期（天） | 到降权线（天） | 到遗忘线（天） |
|---|---|---|---|---|
| 30 天 | 0 | 30 | 53 | 130 |
| 30 天 | 1 | 48 | 84 | 208 |
| 30 天 | 3 | 123 | 214 | 532 |
| 30 天 | 8 | 1288 | 2239 | 5569 |
| 90 天（默认） | 0 | 90 | 157 | 389 |
| 90 天（默认） | 1 | 144 | 251 | 623 |
| 90 天（默认） | 3 | 369 | 641 | 1594 |
| 90 天（默认） | 8 | 3865 | 6715 | 16707 |
| 180 天 | 0 | 180 | 313 | 778 |
| 180 天 | 1 | 288 | 501 | 1245 |
| 180 天 | 3 | 737 | 1281 | 3187 |
| 180 天 | 8 | 7731 | 13429 | 33413 |

用过超过 8 次和用过 8 次一样（次数上限）。每用一次，这些天数从那一次重新算起。对某一条记忆，`forget explain` 会按它自己的账本算出两个年龄、降权的日期和最早可以被删的日期。

## 限速

每次清理、每个存储最多忘 `max(max_forget_min, max_forget_fraction × 该存储的条数)` 条（默认 `max(5, 2%)`；一个 240 条的库每次最多 5 条，一个 1000 条的库 20 条）。到期的比这多时，先忘**删除用的保持率最低**的（保持率相同的按地址排），其余**留下**，报告里叫 `held`，它们在后面的清理里再忘。网关的定时清理每天一次的话，240 条同一天到期的一批大约 48 天忘完。

- 逐个存储算（租户存储各算各的）；条数用的是这次清理开始时存储里的条数，所以存储变小，上限也变小，但不会低于 `max_forget_min`。
- 目的：系统时钟错了、半衰期设错了，一次清理最多损失一小片，而且那一小片是存了档的，`forget restore` 取得回。旧版本的“刹车”（超过比例就整个存储都不删）会让同一天到期的一批永远被拦住；限速让这一批慢慢走掉。
- `forget sweep --force` 对这一次取消限速（引擎里 `Forgetting.sweep(..., force=True)`），到期的全删。网关的定时清理从不这样。
- `--dry-run` 也会报 `held`（真正清理时会留下的条数）。
- 被留下的记忆还在存储里，召回照常；如果在下一次清理前被用到，它的计时重新开始，就不再到期。
- 把 `max_forget_min` 设成 0、`max_forget_fraction` 设成 0，等于不自动删（只有 `--force` 才删）。

## 每项设置

| 设置 | 默认 | 意思 |
|---|---|---|
| `ledger` | 必填 | 账本文件（SQLite）的路径 |
| `archive` | 必填 | 存档文件（SQLite）的路径 |
| `stores` | 必填 | 要管理的共享存储名，或租户提供方名（该提供方下每个租户各管各的） |
| `demote_below` | 0.3 | 降权线（按排序用的保持率），0 到 1；必须大于 `forget_below`。只用于报告的“降权”状态，不改变排序 |
| `max_forget_fraction` | 0.02 | 限速：每次清理、每个存储最多忘 `max(max_forget_min, 这个比例 × 条数)` 条；0 到 1 |
| `max_forget_min` | 5 | 限速的下限：整数，不小于 0 |
| `forget_below` | 0.05 | 遗忘线（按删除用的保持率） |
| `archive_days` | 90 | 存档保留天数，过期后下一次清理时真正删掉 |
| `sweep_every_hours` | 24 | 网关自动清理的间隔小时数；0 = 不自动，只用命令 |
| `pin_refs` | 空 | 通配符列表（`fnmatch` 规则），匹配到的地址永远不忘 |
| `[forgetting.curve] type` | `ebbinghaus` | 曲线；也可以写 `模块:类` |
| `half_life_days` | 90 | 基础半衰期（天） |
| `per_store` | 空 | `{存储名 = 天数}`，按来源分别设基础半衰期；租户存储 `提供方:租户编号` 按提供方名查 |
| `reinforce` | 1.6 | 巩固系数，不小于 1；每用一次半衰期乘以它 |
| `max_uses` | 8 | 次数上限 |
| `freshness` 阶段的 `floor` | 0.7 | 再旧的记忆最多保留的分数比例；新鲜度 = `floor + (1 - floor) × R`，钉住的是 1；0 到 1 |
| `freshness` 阶段的 `credit` | `"top"` | 召回时谁记“用到”：`"top"` 最相关的一条和几乎一样相关的，`"all"` 返回的每一条，`"none"` 都不记（见“用到怎么算”） |
| `freshness` 阶段的 `credit_ratio` | 0.9 | `"top"` 的门槛：相似度不低于最高的这个倍数；大于 0、不大于 1 |
| 客户端的 `pin_writes` | false | 这个客户端写入的记忆自动钉住 |

账本的键（命令里的 STORE）：共享存储用它的名字，租户存储用 `提供方名:租户编号`。

## 命令

所有子命令都带 `--config 配置文件`，按配置建出网关里的存储和账本，不启动服务，用完关闭。没有配置 `[forgetting]` 时，打印怎么打开，退出码 1。输出只有数字和地址（地址里可能有话题名，租户编号也会出现），不显示记忆正文；日期按 UTC。

| 命令 | 做什么 |
|---|---|
| `feiyu-memgate forget status --config F` | 每个被管理的存储（和每个租户）的条数：共多少、钉住、正常、降权（只是报告）、到期；存档大小；线和半衰期。只读，不改任何东西 |
| `feiyu-memgate forget sweep --config F` | 清理一次：同步账本、到期的存档并删除、清存档里过期的；打印每个存储的数字 |
| `feiyu-memgate forget sweep --dry-run --config F` | 只算条数（含限速会留下的条数 `held`），存储、账本、存档都不改 |
| `feiyu-memgate forget sweep --force --config F` | 这一次不受限速（到期的全删）。网关的定时清理从不这样 |
| `feiyu-memgate forget archive --config F [--store KEY]` | 列出存档里的记忆：存储、地址、遗忘日期、到期日期、用过几次。`--show-text` 才显示正文 |
| `feiyu-memgate forget restore STORE REF --config F` | 把存档里的一条写回原来的存储和地址；账本里把它的“最近用到”设成现在，免得下一次清理又删掉它；再从存档去掉 |
| `feiyu-memgate forget pin STORE REF... --config F` | 钉住：排序不打折、永不遗忘。存储里没有的地址不会被钉，会列出来，退出码 1 |
| `feiyu-memgate forget unpin STORE REF... --config F` | 取消手动钉住。匹配 `pin_refs` 规则的仍然不会被遗忘，命令会提醒 |
| `feiyu-memgate forget explain STORE REF --config F` | 账本记着这条记忆什么（记忆日期起点、开始被管理、最近用到、次数、是否钉住）、两个保持率（排序用的、删除用的）各多少、状态，以及如果再没被用到，什么时候越过降权线、最早什么时候可以被删 |

`feiyu-memgate check --config F` 在配置了遗忘时多打印一节“遗忘”：账本和存档的路径、被管理的存储、两条线、曲线类型和选项、每个共享存储有没有需要的能力（`refs`、`delete`、`put`；`receipt_refs` 只用于“写入即钉住”）。

命令可以和正在运行的网关同时使用：账本和存档是 SQLite 文件，两边按各自的连接读写。

## 钉住

三种方式，被钉住的记忆排序时不打折（新鲜度恒为 1），也不遗忘：

- 地址规则 `pin_refs`：通配符。例如 `"*/profile.md"`。
- 写入即钉住：客户端策略里 `pin_writes = true`。用在“主人明确说要记住”的那个令牌上。需要存储能说出一次写入产生了哪些记忆（`receipt_refs`）。
- 手动：`forget pin` / `forget unpin`。

## 要备份、要保护什么

- **账本**：只有地址、时间、次数、是否钉住，没有记忆正文。但地址里可能带话题名，租户存储的键里有租户编号，所以要和记忆本身一样保护。
- **存档**：含被遗忘记忆的**全文**，保护等级和记忆本身一样，不能更低。它在保留期内是恢复的唯一来源。
- 两个文件要一起备份（用 `feiyu-memgate backup seal` 加密打包，把它们所在的目录加进去）。账本丢了，所有记忆“用过几次”归零，“开始被管理”重新算（删除要从头等一个曲线寿命，所以不会更快被删，但排序里会更靠后）；存档丢了，已删的就恢复不了。
- 不要把这两个文件放在可以通过网络访问的目录里，也不要提交进仓库。

## 写自己的曲线

曲线是一块拼图，槽位名 `forgetting_curve`。它只回答一个问题：`retention(age_days, uses, source)` 返回 0 到 1 的保持率，不保存状态。`source` 是存储名；租户存储传的是提供方名。

```python
# my_pkg/curves.py
from feiyu_memgate.forgetting.curve import ForgettingCurve

class LinearCurve(ForgettingCurve):
    """保持率随天数线性下降，每用一次多撑 extra 天。"""

    def __init__(self, days=120, extra=30):
        self.days, self.extra = days, extra

    def retention(self, age_days, uses, source):
        life = self.days + self.extra * uses
        return max(0.0, 1.0 - age_days / life)
```

```toml
[forgetting.curve]
type = "my_pkg.curves:LinearCurve"   # 或者用 @register("forgetting_curve", "名字") 注册后写名字
days = 90
```

配置里除 `type` 以外的项原样作为关键字参数传给构造函数。曲线应该随天数不增（`forget explain` 用二分法找越过两条线的日期，依赖这一点）。`feiyu-memgate pieces` 能列出已注册的曲线。

## 哪些后端能被管理

被管理的存储要有三个可选能力（见 `backends/base.py`）：

- `refs()`：列出存储里**全部**记忆的 `(地址, 日期或 None)`，不一次性载入全部正文；
- `delete(ref)`：删一条，真的删掉了返回 True；
- `put(text, ref=None, date=None)`：把一条记忆按原样写回（恢复时用），需要 `writable = true`。

可选的第四个：`receipt_refs(receipt)`：一次写入产生了哪些记忆，不知道时返回 None。只有“写入即钉住”要用。

内置后端：`inmemory`、`sqlite`、`embedding`、`hybrid`（它的子后端也要有这些能力）都有；`openviking` 有，但要 `writable = true`。自己写的后端，实现这三个方法（需要 `pin_writes` 再加 `receipt_refs`）就能被管理；缺哪个，`check` 和配置加载会说缺哪个。租户提供方要有 `list()`，返回全部租户编号（不能是密钥）。

## 安全特性

- **先存档再删除**：每条记忆按“读全文 → 写存档 → 从存储删除 → 从账本去掉”的顺序处理，任何一步失败，这一条留到下一次，不会出现“删了但没存档”。删除没有成功时，刚写进存档的那份也会去掉，不留一份声称已经删了的记录。
- **HTTP 里没有删除**：对外接口只有召回、写入和 `/v1/used`（只刷新“最近用到”和次数）。
- **演习**：`forget sweep --dry-run` 什么都不改，只给条数；`forget status` 同理。
- **只管列出来的存储**；钉住的永远不删。
- 账本出任何错都不会让召回失败：这一轮新鲜度按 1 算，访问日志里记一个原因词 `ledger-failed`。
- 日志、报告、命令输出里只有数字、存储名和地址，不含记忆正文、问题或密钥。
- 存档超过保留期后，下一次清理才真正删掉。

## 已知限制

- **老库上打开不会当天删库，但同一天开始被管理的一批会在到期后被整批忘掉**：旧版本（删除和排序用同一个保持率）在一个日期跨 21 个月的 240 条库上，第一次清理存档了 192 条；现在删除的计时从“开始被管理”算起，打开当天不会删任何东西（见“打开它”）。同一天开始被管理、一直没被用到的记忆会在同一天一起到期；限速让它们每次清理最多忘 `max(5, 2%×条数)` 条，模拟里（240 条同一天装进来，每天清理一次）183 到 204 条在一个多月内忘完。被忘的都存了档，90 天内取得回；限速只是把这件事放慢、可控，没有让它不发生。
- **默认设置在模拟里的得失**（完整数字见 `bench/results/forgetting/summary.md`）：第 540 天，混合后端存储 240 → 57，关键词后端 240 → 36；冷题（没人问的）Hit@5 混合后端 62.5% → 0.0%，关键词后端 30.0% → 0.0%；噪声率没有稳定改善（混合后端降了，关键词后端升了）；混合后端的热题和温题 Hit@5 和基线一样，**关键词后端的热题 Hit@5 比基线低了 2.5 个百分点（一个题）**，发生在删除之前，是新鲜度重排。
- **钉住身份类只保住身份类**：模拟里钉住 39 条 `identity` 记忆，冷题 Hit@5 混合后端 15.0%，关键词后端 10.0%；其余类型照样被忘。要保住哪一类，就要钉住哪一类。
- **“用到”是网关的猜测，除非客户端明说**：默认的 `credit = "top"` 只给最相关的那几条记一次，比“返回就算”好，但网关仍然不知道模型有没有用它。要准确，让客户端调用 `POST /v1/used`（`MemoryClient.report_used`），并把 `credit` 设成 `"none"`。模拟里没有测这一项。
- **遗忘放大检索的盲区**：一条相关但检索器排不进返回结果的记忆，不会被计为“用到”，会照样老去、到期。关键词后端对换了说法的问题尤其如此（模拟里关键词后端被删的热、温题记忆约是混合后端的 2 倍：39 对 21 条）。
- **OpenViking 的钉住要等整理结束**：先收下、后台再整理的存储，写入时还不知道产生了哪些记忆；网关在后台跟踪这次写入，整理完成后才钉。在那之前网关重启，这次的钉住就丢了，需要用 `forget pin` 补。
- **账本是每个网关各一份**：两个网关共用一个存储、各有各的账本时，A 网关召回用到的记忆，B 网关看来是没用过的，B 的清理可能把它删掉。一个存储只让一个网关的账本管理。
- **参数只是起点**：默认值没有在真实数据上调过。仓库里的 `bench/forgetting_sim.py` 是在假流量上看行为的工具，不是调参的依据。
- 冷门记忆会被忘：这是设计目标，代价是很久没人问的事找不回来，只能在存档期内用 `forget restore` 取回。
- 模拟没有覆盖：记忆陆续写入的库（模拟里 240 条同一天装进来，到期也同一天）、多存储、按来源分别设半衰期、客户端回报、真实的使用分布。有关键词和混合（sqlite + 向量）两个后端；该文件的结论是，在这份数据上这个功能省下了存储，付出了冷题命中率，没有证明得到的比失去的多。
