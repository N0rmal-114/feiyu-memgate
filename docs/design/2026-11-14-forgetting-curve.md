# 遗忘曲线设计

日期：2026-11-14
状态：已实现；2026-11-14 修订（模拟发现了设计缺陷）；2026-11-14 修订二（540 天模拟又发现三个缺陷，见文末）
依据：[记忆改造设计](2026-11-12-memory-redesign.md) 第 4 块，以及其中第 4、5 条决定（到线后先降权再删除，删除前存档 90 天可恢复；身份类信息和主人明确要求记住的永远不忘）。

## 要解决的问题

记忆只增不减：事件一件一个文件，一直累积；召回不看新旧，三年前的事和昨天的事同样可能被翻出来。时间长了，召回里的噪声越来越多，存储也越来越大。

人的记忆不是这样的。不用的事会慢慢淡掉，用到一次就又记牢一些，而且每用一次，下一次淡得更慢。

## 目标

- 很久没被用到的记忆，召回时先往后排，再久就删掉。
- 被用到的记忆会被“巩固”：每用一次，它能保持的时间变长。
- 不同来源忘得不一样快：和主人私聊的最慢，群聊和直播的快。
- 删除可以反悔：删之前全文存档，保留一段时间，可以恢复。
- 有些记忆永远不忘：钉住的，和匹配指定地址规则的（比如身份档案）。
- 整个功能是一块可选的拼图：不配置 `[forgetting]` 就完全没有这回事，现有行为一点不变。
- 曲线本身也是一块拼图，可以换成自己的公式。

## 不做的事

- HTTP 接口里仍然没有删除。删除只由遗忘任务做（网关里的定时任务，或者主机上的命令）。
- 不碰没有列进 `[forgetting].stores` 的存储。
- 记账表里不放记忆内容，只放地址、时间、次数和是否钉住。
- 不调用任何模型。

## 曲线

用艾宾浩斯遗忘曲线的指数形式，写成半衰期：

```
保持率 R = 0.5 ^ ( 距上次用到的天数 / 半衰期 )
半衰期   = 这个来源的基础半衰期 × 巩固系数 ^ min(用过的次数, 上限)
```

- “距上次用到”：从没被用到过的，从这条记忆的日期（没有日期就从记账表第一次见到它的时间）算起。**〔修订：这一条只适用于排序和“降权”；决定“到期”要不要删，改用另一个计时，见文末“修订”。〕**
- “用到一次”：这条记忆被召回、并且真的出现在返回结果里。
- 默认值：基础半衰期 ~~60 天~~（修订：90 天），巩固系数 1.6，次数上限 8。按来源分别设半衰期，例如私聊 180 天、群 30 天。
- 这些默认值是起点，要用评测调。

两条线：

| 线 | 默认 | 到线以后 |
|---|---|---|
| 降权线 `demote_below` | R < 0.3 | 这条记忆进入“降权”状态：召回排序时不再有保底分，沉到后面 |
| 遗忘线 `forget_below` | R < 0.05 | 这条记忆到期：下一次清理时存档、删除 |

按默认值，一条从没被用到的群聊记忆约 52 天后降权、130 天后删除；私聊记忆约 313 天后降权、778 天后删除；被用到过 3 次的私聊记忆，半衰期变成约 737 天。**〔修订：这几个数是按来源分别设了半衰期（群 30 天、私聊 180 天）算的，仍然对；但“删除”的天数现在从“开始被管理”算起，不是从记忆自己的日期算起，见文末。〕**

## 召回时：`freshness` 步骤

一块新的 `recall_stage`，放在 `min_score` 后面（分数线只看相似度）：

- `prepare`：查记账表，算每个候选的保持率 R，分数乘上新鲜度：
  - 正常状态：`新鲜度 = floor + (1 - floor) × R`，`floor` 默认 0.3，所以再旧的记忆也不会因为新鲜度被压到零；
  - 降权状态：`新鲜度 = R`，没有保底；
  - 钉住的：新鲜度恒为 1。
- `finish`（引擎新增的钩子，全部候选处理完以后调用一次）：把真正返回的每条记忆在记账表里记一次“用到”。
- 记账表出任何错都不能让召回失败：这一轮新鲜度按 1 算，访问日志里记一个原因词。

来源权重（`source_weight`）和新鲜度可以叠加，合起来就是设计里的“相似度 × 来源权重 × 新鲜度”。

## 记账表

一个 SQLite 文件，一张表：

| 列 | 意思 |
|---|---|
| `store` | 存储的名字；租户存储是 `提供方名:租户编号` |
| `ref` | 这条记忆在存储里的地址 |
| `first_seen` | 这条记忆的日期，或者记账表第一次见到它的时间（排序用） |
| `managed_since` | **（修订新增）** 记账表第一次知道这条记忆的时间（删除用）；只有 `revive` 会改它 |
| `last_used` | 最近一次被用到的时间，没用到过是空 |
| `uses` | 被用到的次数 |
| `pinned` | 是否钉住 |

没有内容。但地址里可能带话题名，租户编号也在里面，所以这个文件要和记忆本身一样保护。

## 清理：同步、存档、删除

清理任务对 `[forgetting].stores` 里的每个存储做三件事：

1. **同步**：列出存储里现有的全部记忆。记账表里没有的补上（这样从没被召回过的记忆也会变旧；补上的这一刻就是它的 `managed_since`）；记账表里有、存储里已经没有的，去掉。
2. **遗忘**：**删除用的**保持率（见“修订”）低于遗忘线、又没被钉住的，按顺序：读全文 → 写进存档 → 从存储删除 → 从记账表去掉。任何一步失败，这条就留到下次，绝不出现“删了但没存档”。
3. **清存档**：存档里超过保留期（默认 90 天）的，真正删掉。

存储要支持三个可选能力才能被遗忘管理：列出全部记忆（`refs`）、删除一条（`delete`）、写回一条（`put`，恢复时用）。不支持的存储会在检查配置时报出来。

存档是另一个 SQLite 文件，放全文、地址、日期、用过的次数、遗忘时间和到期时间。它里面是记忆内容，要和记忆本身一样保护。

清理可以由网关定时做（`sweep_every_hours`，默认 24，设成 0 就只手动），也可以在主机上运行命令。命令默认只显示条数，不显示内容。

## 钉住

三种方式，都不会被遗忘、也不降权：

- **地址规则** `pin_refs`：通配符，匹配到的地址永远不忘。例如 `"*/profile.md"`。
- **写入即钉住** `pin_writes`：客户端策略里的开关。打开后，这个客户端写入的记忆自动钉住。用在“主人明确说记住这个”的那个令牌上。
- **手动**：主机命令 `forget pin / unpin`。

“写入即钉住”需要存储能说出一次写入产生了哪些记忆（`receipt_refs`）。先收下、后台再整理的存储，等整理结束后再钉。

## 恢复

`forget restore`：把存档里的一条写回原来的存储和地址，记账表里把它的“最近用到”设成现在（否则下一次清理又会把它删掉），再从存档去掉。**〔修订：同时把 `managed_since` 设成现在。〕**

## 配置

```toml
[forgetting]
ledger = "data/ledger.db"
archive = "data/forgotten.db"
stores = ["private", "group"]     # 共享存储的名字，或租户提供方的名字
demote_below = 0.3
forget_below = 0.05
archive_days = 90
sweep_every_hours = 24
pin_refs = ["*/profile.md"]

[forgetting.curve]
type = "ebbinghaus"               # 曲线是一块拼图，可以换成 "你的模块:你的类"
half_life_days = 90               # 修订：原来是 60
per_store = { private = 180, group = 30 }
reinforce = 1.6
max_uses = 8

[clients.owner]
pin_writes = true

[recall]
stages = ["min_score", "freshness", "fill_text", "drop_marker", "redact", "dedupe", "budget"]
```

## 风险

- 清理有删除能力。缓解：只管列出来的存储；删除前必须存档成功；HTTP 接口里没有删除；可以先 `--dry-run` 看条数。
- 默认参数没有在真实数据上调过。缓解：仓库里有模拟工具，可以在假数据上看一年后留下多少、命中率掉多少，再定参数。（模拟已经跑过，发现了下面“修订”里的缺陷。）
- 记账表丢了，所有记忆的“用过的次数”归零，会比原来忘得快。缓解：记账表和存档一起备份。~~同步时用记忆自己的日期作为起点，不会一下子全部到期。~~ **〔这句缓解是错的：恰恰是用记忆自己的日期，才让老库一次清理就全部到期。见文末“修订”。〕**

## 修订（2026-11-14）：模拟发现的缺陷和改法

### 模拟显示了什么

`bench/forgetting_sim.py` 用基准数据（240 条记忆，日期分布在过去 21 个月）模拟 540 天，第一天就打开遗忘。按上面的原设计和默认值（半衰期 60 天）：

- 第一天结束时的第一次清理就存档并删除了 240 条里的 **192 条**。热题的 Hit@5 从 52.5% 掉到 7.5%，之后再没恢复；540 天后库里只剩 4 条。激进设置（半衰期 20 天）第一天就只剩 14 条。
- 原因：保持率从记忆自己的日期算起。凡是比曲线寿命（半衰期 60 天时约 260 天）更老的记忆，账本第一次见到它的那一刻就已经“到期”，它没有任何机会在被管理的状态下被用到。设计里“同步时用记忆自己的日期作为起点，不会一下子全部到期”只对比曲线寿命年轻的记忆成立。
- 结论：**在已有的库上打开这个功能，会删掉大部分内容。** 不可接受。

### 改了什么

**1. 每条记忆两个计时。** 账本新增一列 `managed_since`：账本第一次知道这条记忆的时间。`touch`、`use`、`pin` 在建行时设置，之后不再改；只有 `revive`（恢复）把它设成现在。旧的账本文件自动加上这一列，旧行的 `managed_since` 是迁移的时间。`first_seen` 不变（记忆自己的日期）。

| | 用在哪 | 起点 | 引擎方法 |
|---|---|---|---|
| 排序用的保持率 | `freshness` 阶段打分、“降权”状态 | 最近用到的时间，没用到过就是记忆自己的日期（`first_seen`） | `ranking_retention` |
| 删除用的保持率 | “到期”状态，也就是清理要不要删 | `最近用到` 和 `managed_since` 里**较晚**的那个 | `deletion_retention` |

一条老记忆没人用，排序里照样沉到后面（这是对的）；但它只有在“被管理的状态下，整整一个曲线寿命没被用到”以后才可能被删。打开遗忘不会在第一天删掉任何东西。`status()` 对“到期”用删除用的，对“降权”用排序用的；`forget explain` 同时打印两个年龄，以及最早什么时候可以被删。账本里没有这条记忆（还没被同步）时，删除计时从“现在”算，永远不到期。

**2. 刹车。** `[forgetting]` 新增 `max_forget_fraction`（默认 0.2）。一次清理里，如果某个存储到期的条数超过它的这个比例，这个存储这一次什么都不删，在报告里记 `held`（拦住的条数）。系统时钟错了、半衰期设错了，都不应该清空一个存储。`forget sweep --force`（引擎里 `Forgetting.sweep(..., force=True)`）只对这一次解除；网关的定时清理从不解除。注意：只有一两条记忆的小存储，删一条就超过 20%，要删必须 `--force`。

**3. 更保守的默认。** `half_life_days` 默认 90（原来 60）。巩固系数 1.6、遗忘线 0.05 时，一条从没用过的记忆在被管理 389 天后才可以被删（降权在第 157 天）。文档里的算例已重算。

**4. 账本构建时带上墙上时钟。** `config.build_gateway(..., wall=...)` 现在也把时钟交给账本，否则在假时钟下，给一条还不认识的记忆 `pin` 会盖上真实时间。

### 被取代的句子

上面正文里被这次修订取代的地方，已经在原处用“修订”标出：保持率只有一个计时；默认半衰期 60 天；“同步时用记忆自己的日期作为起点，不会一下子全部到期”这句缓解（它是错的）。其余不变。

### 修订后的模拟（结果见 `bench/results/forgetting/summary.md`）

场景不变（种子、流量、热/温/冷划分、540 天），两个后端（关键词 `sqlite`；`hybrid` = sqlite + `bge-m3` 向量）。上面三条的默认值是在重新运行之前定下的，没有根据结果调整。完整的数字和解读在那份文件里；要点：

- 缺陷修好了：第 1 天两个后端、所有组库里都还是 240 条，一条没删，旧记忆只是降权。
- 默认设置（刹车 0.2）540 天里一条都没有删：240 条记忆同一天开始被管理，没被用到的（关键词后端 201 条，混合后端 97 条）同一天一起到期，刹车每次都拦住。这时功能只剩排序降权。
- 排序降权在混合后端上有代价：什么都没删，热题 Hit@5 97.5% → 85.0%，温题 95.0% → 85.0%。
- 为了看被拦住的是什么，另外跑了“刹车关掉”的探索组：存储小 40%（混合）到 84%（关键词），冷题命中率大降（混合 87.5% → 37.5%，关键词 30% → 0%），噪声没有变好；从存档恢复有效。
- 结论：在这份数据上，这个功能没有证明得到的比失去的多；打开不再删库，这一点做到了。

### 还没解决的

- 所有记忆在同一天装进来、同一天开始被管理时，没被用到的记忆会在同一天一起到期；刹车会拦住这样的集中到期，模拟里默认设置因此 540 天一条都没删。真实的库里记忆是陆续写入的，到期是错开的，这个情况会少得多，但没有真实数据可以验证。
- 排序降权（`freshness`，去掉保底分）本身就让混合后端的命中率掉了 7.5 到 12.5 个百分点。这是排序公式的问题，不是这次修订要解决的；改法方向（只降有更新版本的记忆，或者保留保底分）需要新的设计和新的测量。
- 刹车拦住以后没有自动的出路：要么有人用 `forget sweep --force`，要么等到到期的比例降下来（被用到、被钉住、被恢复）。


## 修订二（2026-11-14）：540 天模拟显示的三个设计缺陷

### 模拟显示了什么

第一次修订之后，在混合后端上跑 540 天（240 条记忆同一天装进来，其余场景不变），第 540 天：

| 组 | 热题 Hit@5 | 温题 | 冷题 | 剩余记忆 |
|---|---|---|---|---|
| 无遗忘 | 97.5 | 95.0 | 87.5 | 240 |
| 默认设置 | 85.0 | 85.0 | 82.5 | 240 |
| 默认设置，刹车关掉 | 85.0 | 85.0 | 37.5 | 143 |

默认设置一条都没删，命中率却掉了 12.5 个百分点；刹车关掉以后才删，而冷题命中率大降。三个缺陷，各自来自设计本身。

### 缺陷一：新鲜度可以埋掉一条很强的匹配

热题 Hit@5 掉了 12.5 个百分点，而且一条都没删。原因：“降权”状态的记忆分数乘的是保持率本身（没有保底），正常状态的乘 `0.3 + 0.7·R`。一条相似度 0.9、保持率很低的记忆，输给一条相似度 0.4、只是碰巧最近被返回过的无关记忆。新鲜度不该有这个权力：相关性必须说了算，新鲜度只是个先验，用来决定“差不多相关”的几条谁先谁后。

**改法**：所有状态用同一个有界系数 `新鲜度 = floor + (1 - floor) · 排序保持率`，`floor` 默认 **0.7**（`freshness` 阶段的选项，原来是 0.3），钉住的恒为 1。再旧的记忆也最多损失 30% 的分数。“降权”不再是排序状态：它只留作报告里的状态词，意思是“排序保持率低于 `demote_below`”，也就是“很快到新鲜度的下限，以后是被删的候选”。`demote_below` 因此不再影响召回。

### 缺陷二：被返回不等于有用

每条被返回的记忆都记一次“用到”，所以一条总是搭车出现在前 5 名里的噪声会被一直保鲜，而一条相关但没人问到的记忆照样老去：越富越富的循环。

**改法（两部分）**：

1. 召回时的计用规则，`freshness` 阶段的选项 `credit`：`"top"`（默认）只有相似度（打折前的分数，`meta["similarity"]`）最高的返回条目，以及相似度不低于它 `credit_ratio`（默认 0.9）倍的条目记一次“用到”；`"all"` 是原来的做法；`"none"` 召回从不记（给用显式回报的部署）。
2. 明确的信号：新路由 `POST /v1/used`，聊天程序告诉网关这次回复真正依赖了哪几条。鉴权、限流、租户和召回一样，客户端必须能从每个 `source` 召回，最多 20 项，格式不对是 400 `bad_used`（新错误码），来源不在客户端能召回的范围里是 403 `forbidden`（不存在的来源和没有权限的来源回答一样，不泄露哪些存储存在）。对每条存在的记忆在账本里记一次“用到”（两个计时都重新算），回 `{"status": "ok", "recorded": n}`；没配置遗忘时回 200、`recorded` 是 0。网关先看账本里有没有这条，没有就问存储能不能读出来，所以编造的 id 什么都不记也不留行，回答里只有“记下了几条”。它只能刷新记忆的时钟，不能删、不能改、不能读出，所以“HTTP 里没有删除”这条仍然成立（`docs/security.md` 已写明）。客户端：`MemoryClient.report_used(items, tenant_id=None)`。

### 缺陷三：刹车把一整批记忆永远冻住

同一天开始被管理的记忆会一起到期，超过 `max_forget_fraction`，每次清理都被拦住，默认设置因此 540 天什么也没删。刹车防住了坏事，也防住了好事，而且没有出路。

**改法**：刹车改成限速。每次清理、每个存储最多忘 `max(max_forget_min, max_forget_fraction × 该存储条数)` 条，先忘**删除用的保持率最低**的（相同的按地址排），其余留下，报告里是 `held`，后面的清理再忘。默认 `max_forget_fraction = 0.02`（原来 0.2），`max_forget_min = 5`（新增）。时钟错了、半衰期设错了，代价是每次清理最多一小片，而且是存了档、可以恢复的，不再是整个存储。`--force` / `force=True` 对一次运行取消限速。网关后台清理的日志行加上了 `held`。

### 一起改的东西

- `tests/test_cli.py` 的 22 个错误（“名字已经注册给另一个拼图”）：原因不是测试之间的名字冲突，而是 `mock.patch.dict(sys.modules, ...)` 退出时会忘掉在它里面第一次导入的模块（CLI 懒导入的 `tenants.keyfile` 等），再导入一次就用新的类重新注册。注册表的规则没动；测试文件一开始就把这些模块导入。
- 模拟（`bench/forgetting_sim.py`）：不再手设分数线，用网关默认的一套召回步骤，只在 `min_score` 后面、`relative_score` 前面插入 `freshness`；去掉“刹车关掉”组，新增“默认设置 + 钉住身份类（`kind` 为 `identity` 的 39 条）”组。四组在跑之前定下，之后没有改。

### 修订二之后的模拟（结果见 `bench/results/forgetting/summary.md` 和 `reading.md`）

场景不变（种子、流量、热/温/冷划分、540 天，两个后端）。四个组在跑之前定下：无遗忘；默认设置；默认设置 + 钉住 39 条 `identity`；激进设置（半衰期除以 3）。召回步骤用网关的默认一套（各后端自己的默认分数线），只在 `min_score` 后面插入 `freshness`。第 540 天：

| 后端 | 组 | 库内 | 热 Hit@5 | 温 | 冷 | 噪声率 |
|---|---|---|---|---|---|---|
| 混合 | 基线 | 240 | 87.5 | 77.5 | 82.5 | 27.2 |
| 混合 | 默认 | 71 | 90.0 | 75.0 | 5.0 | 24.4 |
| 混合 | 默认 + 钉住身份类 | 98 | 87.5 | 75.0 | 25.0 | 23.5 |
| 混合 | 激进 | 70 | 90.0 | 75.0 | 5.0 | 28.4 |
| 关键词 | 基线 | 240 | 72.5 | 37.5 | 47.5 | 26.7 |
| 关键词 | 默认 | 46 | 70.0 | 37.5 | 0.0 | 27.1 |
| 关键词 | 默认 + 钉住身份类 | 75 | 70.0 | 37.5 | 12.5 | 30.4 |
| 关键词 | 激进 | 44 | 70.0 | 37.5 | 0.0 | 24.6 |

- 缺陷一修好了大半：混合后端热题的降幅从 12.5 个百分点降到 0，温题降了 2.5（一个题）；关键词后端热题降了 2.5。**热题或温题仍然比基线低 2.5 个百分点（一个题），发生在删除之前，没有为了让它好看而调任何东西。**
- 缺陷三修好了：默认设置不再什么都不删，到期的一批在约 35 到 40 天里被限速忘完，都存了档。
- 得到的：存储缩小 70% 到 81%。付出的：冷题命中率几乎归零（钉住身份类后 25% / 12.5%）；噪声率没有稳定改善。结论仍然是：在这份数据上这个功能没有证明得到的比失去的多；它让存储变小是真的，代价是没人问的事找不回来（存档期内可以恢复）。
- 缺陷二（计用规则）的单独贡献没有测：模拟里没有只改这一项的对照组，也没有测客户端回报。

### 还没解决的

- 模拟里所有记忆在同一天装进来，到期也在同一天；真实的库陆续写入，限速几乎不会起作用，没有真实数据可验证。
- 新鲜度即使有界，仍然会重排几个题（2.5 个百分点）；`floor` 默认 0.7 是在看这份结果之前定的，没有为它调过。
- 钉住只保住被钉住的那一类；要不要给更多类型默认的保护，需要真实使用的数据。
