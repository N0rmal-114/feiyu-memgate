# 内置后端补充：打分、默认值与限制

`sqlite` 只认字面，`openviking` 需要另外部署一个服务。`embedding` 和 `hybrid` 补上中间那一档：
只要有一个 embeddings 接口，就能做语义检索。它们和其他后端一样是普通的可选部件，在配置里用 `type` 选用。

## 各后端的分数和分数线一览

每个后端的分数含义不同，所以各自声明两组分数线。下表是 `precise` 档的一组：`default_min_score` 和 `default_relative_ratio`
（`default_` 前缀是历史命名，指的是 precise 这一档，不是默认档位；默认档位是 `broad`，它的分数线在下一节，见 [pieces.md](pieces.md)）。
网关的 `min_score` 和 `relative_score` 两个阶段不写 `profile` 时用 `broad` 的一组，写了 `profile = "precise"` 才用下表：

| 后端 | 分数是什么 | `default_min_score` | `default_relative_ratio` |
|---|---|---|---|
| `sqlite`、`inmemory` | 按稀有程度加权的字面重合度（见下） | 0.30 | 0.75 |
| `embedding` | 余弦换算成 0..1（`floor`、`ceil` 按模型预设，bge-m3 是 0.40 / 0.80） | 按模型预设，bge-m3 是 0.50（余弦 0.60） | 按模型预设，bge-m3 是 0.85 |
| `hybrid` | 子后端分数的概率“或” | 0.70 | 0.85 |
| `openviking` | 校准后的相关度 | 0.55（原始分数 0.775） | 0.95 |

## 两档分数线：`broad`（默认）和 `precise`

`precise` 档（上表）偏向精确和安静：宁可不答，也不交一堆杂项，每题约交 1 条。代价是换了说法问的问题常常漏答。
所以每个后端还声明了第二组值 `broad_min_score` 和 `broad_relative_ratio`，用 `min_score` / `relative_score` 的选项 `profile = "broad"` 选用，
或者在配置里写 `[recall] profile = "broad"`（见 [configuration.md](configuration.md)）。**`broad` 现在是默认档位**：项目用在聊天陪伴上，
一个话题通常牵到好几条记忆，每轮只交 1 条太少。`broad` 有代价：多答对一些题，交出去的条目更杂，对没有答案的问题也更容易开口。
要回到以前的行为，写 `[recall] profile = "precise"`。两档的数值没有改动。

选值的规则和默认值一样事先写定，用同一份开发集 `bench/dev`、同一份候选列表、同一张网格和同一套真实的召回步骤
（`python bench/dev_eval.py --backend <后端> --search --profile broad`，输出在 `bench/results/dev/<后端>.md`，不带后缀的名字是默认档位的记录）：

> 在精确率 >= 50% 且安静率 >= 该后端 precise 点安静率一半的格子里，取交付命中最高的；平手取 `balanced` 高的，
> 再取 `min_score` 高的，再取比例高的（不用 `relative_score` 算最低）。选出的点就是 precise 点时，这个后端没有独立的 `broad`，
> 它的 `broad` 回落到 `default_*` 的值。

开发集上的结果（80 个可答问题、30 个没有答案；不是留出集的成绩；每格是 precise → broad）：

读法：

- 每个后端都找到了一个和默认点不同的 `broad` 点，所以这里没有“回落”的后端；自己写的后端不声明 `broad_*` 时，两档对它都用它的 `default_*` 值。
- 代价比收益大：向量和混合后端交付命中多 7 到 24 个点，精确率少 11 到 30 个点，没有答案的问题开口的概率多 7 到 33 个点，
  每题多交 0.7 到 1.5 条（占上下文）。精确率多数贴近 50% 的下限：规则只保证不低于它。
  所以默认的 `broad` 适合“别漏”比“别吵”重要、又能承受杂项的用法（聊天陪伴）；上下文紧、要少而准时切到 `precise`。`sqlite` 的收益最小（关键词匹配对改写题本来就给不出分数）；`openviking` 的差别最小，它的 precise 点本来就比较宽松。
- `bge-base-zh` 的选点（0.05 / 0.50）落在网格的下边缘，`bge-small-zh` 的 0.10 也靠近边缘；网格是事先定的，没有往外扩。
- `hybrid` 的 `broad` 是用 bge-m3 子后端选的；`hybrid` 没有按模型的预设，换别的向量模型时两个值不跟着变，
  要自己用 `bench/dev_eval.py --backend hybrid --search --profile broad` 重选。

  `broad` 是在这次的候选列表上选的。
- `profile` 只是换了一组分数线，`value` / `ratio` 写出来的数永远优先。开发集不大（最小的题型 12 题），几个点的差距不是结论。

## 写入时记忆的日期

`sqlite`、`embedding`、`hybrid`、`inmemory` 的 `remember()` 用消息自己的 `time` 定这条记忆的日期：`time` 是字符串，开头十个字符是真实存在的 `YYYY-MM-DD` 日期，第十一个字符（有的话）是 `T` 或空格（`2026-11-17`、`2026-11-17T08:30:00+08:00`、`2026-11-17 08:30` 都行；`2026-11-171`、`2026-02-30`、`2026/11/17` 不行），日期就取这十个字符，不做时区换算。没有 `time` 或不合格时和以前一样：`sqlite`、`embedding`、`hybrid` 用当天的 UTC 日期，`inmemory` 不记日期。`put()` 不变，还是用传入的 `date`。`time` 和 `speaker` 本身仍然不存。

`openviking` 不涉及：它把整段对话交给 OpenViking 整理，日期由 OpenViking 决定。

## sqlite 与 inmemory：按稀有程度加权的字面检索

两者打分相同。把文字规范化后（去掉空白和标点、全角转半角、转小写）切成“字”：每个相邻两字组合（二元组），
再加上每个单独的汉字（所以中文不需要分词）。`sqlite` 把它们建成倒排索引，用来找出和问题有共同字的记忆；
`inmemory` 在内存里数。

**打分**：`score = 问题里出现在记忆中的字的权重之和 ÷ 问题里所有字的权重之和`，范围 0..1，问题的字全在记忆里就是 1。
一个字的权重是它在这个库里的 BM25 逆文档频率 `ln(1 + (N - df + 0.5) / (df + 0.5))`（`N` 是记忆条数，`df` 是含这个字的
记忆条数；没有任何记忆含有的字按 `df = 1` 算，所以错别字不会压倒整个问题）。几乎每条记忆都有的字（“的”“什么”）
权重很小，只有少数记忆有的字权重很大。这比“问题的二元组有多少在记忆里”更能把真正相关的和只是撞上常用字的分开
（开发集上，同样的分数线下，有答案的问题命中 100%、噪声 17%，旧打分在差不多的噪声下命中约 70%）。

开发集上也比较过标准 BM25（按问题自身的得分归一）：Hit@5 相同，但分数被压得很低，分数线很难定，所以留了
加权重合度。单独汉字有没有用：加了以后 Hit@1 从 90.9% 到 95.5%，答案命中在同样噪声下高出约 20 个百分点，所以保留；
开发集小，这是“看起来有用”，不是结论。

**限制**：
- 不懂意思：换了说法、一个字都不重合的改写找不到。
- 每次最多读 `max_postings`（默认 20000）条索引、给 `max_candidates`（默认 2000）条记忆打分；候选按“共有字的权重之和”挑，
  所以长问题和大库的耗时有上限。
- 一个字出现在多少条记忆里，数到 500（`DF_PROBE`）为止；更常见的字按 500 算，权重略偏大。只有记忆远多于 500 条时才有影响。
- 100k 条记忆的合成基准（`FEIYU_MEMGATE_SLOW_TESTS=1`）：12 个字的查询 p95 0.037 秒 → 0.041 秒，
  500 个字的 p95 0.052 秒 → 0.071 秒（多出的是单字的频率探测和权重计算）。
- 旧版本建的库只有二元组索引：可写方式打开时会一次性重建索引（遍历所有记忆文字），只读方式打开就继续只按二元组搜索。

## embedding：只靠 embeddings 接口的向量检索

记忆原文和向量存在一个 SQLite 文件里。写入时调用 `POST <url>/embeddings`（兼容 OpenAI 的接口，
Ollama、vLLM、各家云端都可以）取向量并归一化；查询时给问题取向量，再和库里所有向量做点积（余弦）排序。
只用标准库。

| 选项 | 默认 | 说明 |
|---|---|---|
| `path` | 必填 | 存文字和向量的 SQLite 文件；`":memory:"` 用于测试 |
| `url` | 必填 | embeddings 接口的基地址，如 `http://127.0.0.1:11434/v1`（只允许 http/https） |
| `model` | 必填 | 模型名；库里记住建库用的模型，换模型会拒绝打开旧库 |
| `key` | 无 | 可选的 Bearer 密钥；用 `key_env = "变量名"` 从环境变量读 |
| `writable` | `true` | `false` 时拒绝写入 |
| `roles` | `["user"]` | `remember` 保存哪些角色的消息 |
| `timeout` | `10.0` | 单次请求的套接字超时，也是一次调用的默认总时限（秒） |
| `batch` | `32` | 每个 embeddings 请求带多少条文字 |
| `floor` / `ceil` | 模型预设（见下） | 余弦相似度换算成 0..1 相关度的区间；没有预设的模型是 `0.40` / `0.80` |
| `query_prefix` | 模型预设（多数是空） | 取查询向量前加在查询前面的文字（比如检索指令）；只用于 embeddings 请求，不改任何存下或返回的文字 |
| `document_prefix` | 模型预设（目前都是空） | 取记忆向量前加在记忆文字前面的文字；和 `model` 一样记在库里，换了会拒绝打开旧库（要打开旧库就写成建库时用的值） |

**分数**：不相关的两段文字，余弦相似度也常有 0.3 到 0.45，不能直接当相关度。后端用
`score = clamp((余弦 - floor) / (ceil - floor))` 换算，低于 `floor` 的记忆不返回；原始余弦放在
`Hit.meta["cosine"]`（`Hit` 有 `meta` 字段时）。不同模型的余弦分布差得很多，所以后端带一张按**模型名**
匹配的预设表（`backends/embedding.py` 里的 `PRESETS`，模型名里含该字样即匹配，不分大小写），每一行给出
`floor`、`ceil`、`default_min_score`、`default_relative_ratio` 和两个前缀；同名选项写了就覆盖预设。
`default_min_score` 和 `default_relative_ratio` 因此是每个后端实例自己的值，不再是全局常数。

| 模型（匹配字样） | 维度 | `floor` / `ceil` | `default_min_score` | `default_relative_ratio` | `query_prefix` |
|---|---|---|---|---|---|
| `bge-m3` | 1024 | 0.40 / 0.80 | 0.50 | 0.85 | 无 |
| `bge-small-zh` | 512 | 0.40 / 0.80 | 0.30 | 0.90 | 无 |
| `bge-base-zh` | 768 | 0.35 / 0.80 | 0.25 | 0.75 | BAAI 的检索指令 |
| `embeddinggemma` | 768 | 0.30 / 0.75 | 0.55 | 0.85 | 无 |
| `qwen3-embedding` | 1024 | 0.35 / 0.80 | 0.20 | 0.95 | Qwen 的 `Instruct: ...
Query:` |

bge-m3 一行是原来的默认值（`floor`、`ceil` 在 `examples/eval` 上用 bge-m3 定，分数线在 `bench/dev` 上按上面的规则选）。
其余四行来自实验 `bench/experiments/light_models/`（只用开发集 `bench/dev`）：`floor` 用一条不需要问题的固定配方
（库里所有记忆两两余弦的平均值减 0.05，取整到 0.05；`ceil` = `floor` + 剩余区间（1 - `floor`）的 2/3，取整到 0.05；
这条配方在 bge-m3 上正好给出 0.40 / 0.80），分数线是 `bench/dev_eval.py --search` 的网格里 `balanced` 最高的点。
前缀按各模型的说明比较过：没有前缀和推荐前缀，按排名的 MRR@10、再按 Hit@5 取好的那个；推荐前缀只在 bge-base-zh 和
qwen3-embedding 上更好，所以只有这两行带前缀（embeddinggemma 官方的 `task: search result | query: ` 和
`title: none | text: ` 在这份数据上反而更差）。Ollama 自己不给这些模型加前缀（它们的模板是原样的提示词）。

**没有预设的模型**会用 0.40 / 0.80 / 0.50 / 0.85（bge-m3 的数值）、不加前缀，并在启动时往日志（`feiyu_memgate.backends.embedding`，
每个模型名每个进程一次，不含文字和密钥）写一条警告：这些数是猜的，请用 `bench/dev_eval.py --search` 在自己的数据上校准，
再把 `floor`、`ceil` 写进配置（写了任何一个，警告就不再出）。**换前缀等于换了向量**：库记住 `document_prefix`，不一致就拒绝打开。
**查询自适应换算**（按每个问题自己的余弦分布换算分数）也比较过，没有采用，见 `bench/experiments/light_models/README.md`。

**换不同大小的模型**：模型越轻，向量越短、取一次向量越快，但开发集上的排名和交付都会下降一些；各档的实测数字
（内存、延迟、入库时间、库文件大小、开发集指标）见 `bench/experiments/light_models/README.md`。

**擅长**：换了说法的问题（“他几点睡觉”对“凌晨一点前睡觉”）；中英文混合；不需要分词。

**不擅长**：
- 暴力扫描，没有索引。向量缓存在内存里（float32，1024 维 5 万条约 200 MB）。单核实测（1024 维随机向量，
  不含取查询向量的时间）：1 万条约 0.14 秒、5 万条约 0.9 秒一次搜索。个人记忆（几千到几万条）够用，
  超过十万条请换真正的向量库。
- 每次搜索都要先请求一次 embeddings 接口（最近 256 个查询有缓存），接口慢或不可达时搜索会失败
  （抛 `BackendError`，不会卡住）。
- 所有记忆文字都会发给 embeddings 接口。
- 对数字、专有名词、很短的词不如关键词稳。

另有可选能力：`put` / `put_many`（批量取向量，导入大量数据用）/ `delete` / `refs` / `receipt_refs` /
`count` / `items`。`health` 只检查库能不能读，不会请求 embeddings 接口。

## hybrid：关键词与向量融合

把几个后端包成一个：写入同时进每个子后端（同一个 ref），查询时问每个子后端再按 ref 融合。
典型用法是 `sqlite`（字面准、零成本）加 `embedding`（找改写）。

| 选项 | 默认 | 说明 |
|---|---|---|
| `children` | 必填 | 子后端列表，每项是带 `type` 的表；可写时子后端必须有 `put` 和 `delete` |
| `weights` | 全 1.0 | 每个子后端一个权重，限制在 0..1（融合公式里的 wᵢ） |
| `writable` | `true` | `false` 时拒绝写入 |
| `roles` | `["user"]` | `remember` 保存哪些角色的消息（每条放进每个子后端） |
| `timeout` | `10.0` | 调用方没给时限时，一次搜索的总时限（秒），在子后端之间平分剩余时间 |

**融合**：网关按 `score` 排序，所以融合分数本身就是排序依据，且仍是 0..1 的相关度：
`1 - ∏(1 - wᵢ·sᵢ)`（概率“或”）。两个子后端都喜欢的记忆排在只有一个喜欢的前面，只有一个子后端很确定时
分数依然很高。每个子后端各自的分数放在 `Hit.meta["child_scores"]`（`Hit` 有 `meta` 时）。

**融合方式是比较过的**，结论是：在 bge-m3 这样强的向量模型上，融合没有带来可用的收益，所以保留概率“或”。
实验在 `bench/experiments/fusion/`（只用开发集 `bench/dev`：160 条记忆，110 个问题，其中 38 个改写题、30 个没有答案）。
每个子后端各取前 45 条候选，离线走真实的默认召回阶段，网格和 `balanced` 目标与 `bench/dev_eval.py --search` 相同；
先复现了上面的 `hybrid` 结果（完全一致），再比较：

| 方式 | Hit@1 | Hit@5 | 交付命中 | 精确率 | 安静率 | balanced | 改写题交付 |
|---|---|---|---|---|---|---|---|
| 只用 `sqlite` | 53.8 | 82.5 | 36.2 | 84.8 | 86.7 | 60.6 | 2/38 |
| 只用 `embedding`（默认点 0.50 / 0.85） | 82.5 | 97.5 | 77.5 | 83.7 | 60.0 | 74.9 | 26/38 |
| A 概率“或”（现用，0.70 / 0.85） | 82.5 | 98.8 | 68.8 | 88.5 | 73.3 | 76.3 | 20/38 |
| B 取较大者 | 82.5 | 97.5 | 77.5 | 83.7 | 60.0 | 74.9 | 26/38 |
| C 先按各自默认分数线校准再“或” | 81.2 | 98.8 | 66.2 | 89.0 | 76.7 | 76.1 | 19/38 |
| D 校准后取较大者，两路都过线再加一点 | 83.8 | 97.5 | 66.2 | 88.4 | 73.3 | 75.1 | 18/38 |
| E 按名次融合（RRF）定顺序，校准后的较大者当分数 | 72.5 | 91.2 | 67.5 | 83.4 | 76.7 | 75.2 | 21/38 |
| F 概率“或”，关键词权重 0.5（看过数据后加的） | 83.8 | 98.8 | 68.8 | 85.6 | 73.3 | 75.4 | 20/38 |
| G 概率“或”，关键词权重 0.25（同上） | 85.0 | 98.8 | 67.5 | 87.4 | 73.3 | 75.4 | 19/38 |

（每行是它自己在网格上 `balanced` 最高的点，Hit@1 和 Hit@5 是不设分数线的前 10 名。）按事先定的规则（Hit@5 与 A 相差不超过 1 题、
安静率不低于 A 减 5 个点、`balanced` 要比 A 高出至少 1 个问题的分量即 0.9 个点），没有任何方式胜过 A：B 的安静率掉了 13 个点，
E 的 Hit@5 少了 6 题，其余的 `balanced` 都比 A 低。所以默认值和融合公式都没有变。

怎么看这张表：
- **混合后端只是把交付命中换成了安静率，不是净收益。** 和只用 `embedding` 比，A 的 `balanced` 高 1.4 个点（约 1.5 个问题），
  但改写题交付从 26 降到 20，而且这 6 题 `embedding` 交付、A 交不出；安静率从 60.0% 升到 73.3%，只用 `embedding`
  把分数线抬到 0.60 也能换到差不多的点（交付命中 70.0%、安静率 70.0%，见 `bench/results/dev/embedding-precise.md`）。
- **原因已经核实**：改写题里正确记忆的关键词分数平均只有 0.15（38 题里只有 2 题达到 `sqlite` 自己的分数线 0.30，4 题是 0），
  所以融合分数几乎就是向量分数；而没有答案的问题里最高的关键词分数平均是 0.23，比改写题的正确答案还高（共用主题词）。
  “或”把杂项抬得和答案一样多，于是分数线只能抬到 0.70；改写题里正确记忆的向量分数在 0.50 到 0.70 之间的有 16 题，抬线以后，原来交得出的 6 题交不出去了。
  F、G 把关键词权重调低没有帮助：开发集上这一路带来的是噪声，不是信息。
- **按名次融合最差**：关键词一路把杂项排在前面，名次不带绝对相关度，Hit@5 掉到 91.2%。
- 关键词一路真正有用的地方是字面题（`sqlite` 单独 26/30），而 `embedding` 在这些题上已经是 29/30。

所以：**在 bge-m3 这样的强向量模型上，推荐直接用 `embedding`**（交付命中高、少一个子后端、不用维护两个库）。
`hybrid` 值得考虑的情况只有：想要比 `embedding` 默认点更高的安静率，又愿意损失约 6 题改写题的交付；或者向量模型较弱、
关键词一路能补上它。后一种情况还没有测过（之后会用小模型重跑 `bench/experiments/fusion/fusion_eval.py`，它接受模型名、
接口地址和 `embedding` 子后端的 `floor`、`ceil` 作为参数）。表里的数字只是开发集上的选择依据，不是系统表现。

**分数线要比两个子后端都高**：两个很弱的信号会加起来（“或”），所以 `hybrid` 的 `default_min_score` 是 0.70，
`default_relative_ratio` 是 0.85（在 `bench/dev` 上按上面的规则选；之前是 0.55 和 0.8）。分数线低时弱的一致也能过线，
没有答案的问题就不再安静；分数线高时正确答案开始交不出去，选的是这两头之间 `balanced` 最高的格子。

**故障处理**：搜索时某个子后端出错，这一次搜索跳过它，其余照常回答；全部出错才抛 `BackendError`。
写入是“全成功或全撤销”：任何子后端写失败，已写入的会被 `delete` 撤回（尽力而为；对已存在的 ref 做覆盖写入
失败时，这条旧记忆也会被撤掉，需要重新写入）。

**注意**：
- `children` 是列表，配置里通用的 `*_env` 规则不会进到列表里，所以 hybrid 自己解析子后端里的 `key_env`
  （从进程环境变量读，没设置会报错并说出变量名）。
- 融合假设各子后端的分数含义相近（都是相关度）。`sqlite` 的分数是“问题里的字（按稀有程度加权）有多少出现在记忆里”，
  `embedding` 是换算后的余弦；接别的后端时请先看它们的分数分布。
- 搜索要依次问每个子后端，延迟是它们之和；`refs`、`count`、`items` 取第一个子后端的。

示例配置见 `examples/hybrid/gateway.toml`。

## openviking：对真实服务器的核对和分数校准

`openviking` 后端连一个 OpenViking 账号（选项见 configuration.md 的 `[stores.<名字>]`），搜索用它的
`POST /api/v1/search/find`。它原来只在手写的假服务器上测过；现在对真实的 OpenViking v0.5.3
（镜像 `ghcr.io/volcengine/openviking`，一次性容器，bge-m3 做向量）核对过，发现并修了三处。

| 选项 | 默认 | 说明 |
|---|---|---|
| `floor` | `0.5` | 原始分数里相当于“完全不相关”的值（含），低于它的记 0 分 |
| `ceil` | `1.0` | 原始分数里相当于“完全相关”的值，高于它的记 1 分，必须大于 `floor` |

**分数校准。** OpenViking 的 `find` 分数对任何问题都偏高：在开发集（`examples/eval`，46 条记忆、30 个问题，
其中 8 个记忆里没有答案）上，答得出的问题里正确记忆的分数是 0.79 到 0.89，没有答案的问题里排第一的记忆是
0.64 到 0.79。不校准的话网关默认的 `min_score` 什么都滤不掉，没有答案的问题也总会拿到 5 条（基准里安静率 0%）。
后端像 `embedding` 一样换算：`score = clamp((原始分数 - floor) / (ceil - floor))`，原始值留在
`Hit.meta["raw_score"]`。默认 `floor 0.5`、`ceil 1.0`（在 `examples/eval` 上定的，没有动）。后端自己声明的 `default_min_score` 是 0.55（原始分数 0.775）、
`default_relative_ratio` 是 0.95，是在大开发集 `bench/dev` 上按上面的规则选的（之前没有声明比例，用网关通用的 0.6，
分数线 0.5：在 `bench/dev` 上交付命中 97.5%，但精确率只有 23%、安静率 23%，平均每题交 4.1 条）。
`floor`/`ceil` 在小开发集上的依据：22 个有答案的问题都还有正确记忆（31 条应命中的记忆保留 30 条），8 个没有答案的问题有
7 个什么都不返回（第 8 个的最高分是 0.787）。

边界要说清楚：分数线两边靠得很近。有答案的问题里，最好的错误记忆也能到 0.84，校准只能挡掉
“没有答案”的问题，挡不住答案旁边的杂项（0.75 以上仍有 63 条错误记忆）。开发集只有 46 条记忆，库大得多时
最高的错误分数会更高。**这组默认值依赖向量模型**（用的是 bge-m3）：换了模型或库大了很多，要重新量：把一小批记忆
和问题（含没有答案的）装进一次性的服务器，打印正确记忆、最好的错误记忆、没有答案的问题的原始分数，
把 `floor` 和想要的分数线放在它们之间。

**对真实服务器核对出来的差别**（都已修好，假服务器也改成和真的一样）：

- `refs()` 以前翻 `GET /api/v1/fs/ls?recursive=true`，真实服务器上它只列目录不列文件，240 个文件一个也没看见，
  而且看起来一切正常。现在按服务器自己的 `/openapi.json` 用 `GET /api/v1/fs/tree`（`level_limit=10`、
  `node_limit`、`offset`）翻页，240 个文件 240 个都在。原有的保护都在：同一个 URI 出现两次说明分页坏了，报错；
  页数有上限；只认不是点开头、不在 `skip_names` 里的 `.md` 文件。目录层数超过 10 层的文件不会被列出。
- `delete()` 对不存在的文件，服务器回 200 而不是 404。`estimated_deleted_count` 数的是索引记录，刚写入还没
  建好索引的文件删除时也是 0，所以不能只看它；现在先用 `GET /api/v1/fs/stat`（不存在回 404）问一下，
  不存在就回 `False`，存在才删，回 `True`。
- 真实核对到的：`put` 后 `read` 一致，再 `put` 同一个地址会覆盖，删掉再 `put` 回去 2 秒左右又能搜到。
- `receipt_refs`：对一次真实的会话提交（一次 LLM 抽取，约 9500 个 token）核对过，
  `<会话>/history/archive_001/memory_diff.json` 的版式和后端的假设一致，返回的两条记忆 URI 和
  `refs()` 里新出现的两条相同。

核对脚本在 `bench/adapters/openviking/`（`capabilities.py`、`receipt_check.sh`），只在 v0.5.3 上跑过；
服务器升级后请重跑。
