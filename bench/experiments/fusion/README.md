# 混合后端的融合方式实验

只用开发集 `bench/dev`（160 条记忆、110 个问题：lexical 30、paraphrase 38、updated 12、quiet 30）。不碰留出集。

## 怎么跑

```
# 1. 两个子后端各自的候选（前 45 条，只存编号和分数；需要 embeddings 接口，下面是 docker 内网的例子）
python bench/experiments/fusion/fusion_eval.py --collect --embed-url http://fmg-bench-embedder:11434/v1
# 2. 离线比较各种融合方式（用 bench/dev_eval.py 的网格、真实召回阶段和 balanced 目标）
python bench/experiments/fusion/fusion_eval.py
```

换模型重跑：`--model`、`--embed-url`、`--floor`、`--ceil`，以及向量子后端自己的默认分数线 `--embed-min`、`--embed-ratio`
（校准要用）。候选缓存 `child_candidates.json` 约 280 KB，只含编号和分数，用完删除；输出写在 `results.txt`。

## 事先定的规则

网格和 `bench/dev_eval.py --search` 相同，按 `balanced` 选点。一种方式要被采用，Hit@5（前 10 名、不设分数线）与 A 相差
不超过 1 题，选定点的安静率不低于 A 减 5 个点；合格者里 `balanced` 最高的胜出，平手看 Hit@1，再看简单程度
（A、B、C、D、E 的顺序）；胜者必须比 A 的 `balanced` 高出至少 1 个问题的分量（1/110，0.9 个点），否则保留 A。

## 方式

A 概率“或”（现用）；B 取较大者；C 先把每个子后端的分数换算成“它自己的默认分数线对应 0.5”（`s / (2 x 默认线)`，截到 0..1）再“或”；
D 换算后取较大者，另一路也过线时加上剩余空间的 10%；E 名次融合（RRF，k = 60）定顺序，分数是换算后的较大者，沿 RRF 顺序
取 `min(自己的分数, 前一名分数 - 1e-9)`，所以顺序恰好是 RRF 的顺序、没有记忆的分数高过它自己的换算分，网关按分数排序时
一个数字同时管排序和分数线。F、G 是**看过数据后加的**：概率“或”，关键词权重 0.5 和 0.25。

## 结果

完整输出见 `results.txt`；A 复现了 `bench/results/dev/hybrid.md` 的所有数字。

改写题里 embedding（默认点）交付 26 题：A 交付其中 20 题、漏 6 题；C、D 各漏 8 题。

## 结论

规则下 A 保留：B 的安静率比 A 低 13 个点（不合格），E 的 Hit@5 少 6 题（不合格），C、D、F、G 合格但 `balanced` 都更低。
A 的 `balanced` 比只用 embedding 高 1.4 个点，但这是拿改写题的交付（26 到 20）换来的安静率（60.0% 到 73.3%），
只用 embedding 抬高分数线也能换到差不多的点。原因：改写题里正确记忆的关键词分数平均 0.15，没有答案的问题里最高的关键词分数
平均 0.23，关键词一路在这类数据上带来的是噪声。更弱的向量模型上是否不同，没有测。
