## 怎么读这个结果

下面的数字是这一份场景、这一份数据、这两个后端的结果，不是一般结论。可答的问题只有 120 个，热、温两组各 40 题，**一个题是 2.5 个百分点**；每个设置只跑了一次（种子固定，重跑得到同样的数）。四个组（基线、默认、默认加钉住身份类、激进）在跑之前就定下，看到结果后没有改任何设置。

这一版用的是网关默认的一套召回步骤（`min_score`、`relative_score`、`newer_first` 等，各后端自己的默认分数线，在开发集 `bench/dev` 上选的），只在 `min_score` 后面插入 `freshness`，没有手设任何分数线。所以基线本身是“默认阈值下的检索”：关键词后端基线只交付很少的条目（每题 0.42 条），Hit@5 热题只有 55.0%、温题 32.5%，混合后端是 70.0% 和 62.5%。**这是默认阈值偏严的结果，不是遗忘造成的**；遗忘的效果要看每个组和同一后端基线的差。

### 先说醒目的：有的组的热题或温题 Hit@5 比基线低了 2.5 个百分点

- 关键词后端：热题 55.0% → 52.5%，默认组和激进组都是，从第 30 天起，也就是任何记忆被删之前（冷题的期望记忆从第 390 天才开始被删）。这是新鲜度重排挤掉了一个题，不是删除。温题没变。钉住身份类那一组的热题反而是 57.5%（比基线高 2.5 个点，也是一个题，同样是排序的小扰动，不是“钉住有益”的证据）。
- 混合后端：默认组和钉住组的热题、温题都和基线一样（70.0%、62.5%）；激进组温题 62.5% → 60.0%。
- 一个题的差别，样本太小，不能说是“稳定的 2.5 个点”，但也不能说没有。没有为了让它好看而调任何东西。

### 得到了什么（第 540 天，这份场景、这些设置）

- **存储变小**：混合后端 240 → 57（默认）、85（钉住身份类）、55（激进）；关键词后端 240 → 36、67、36。这批 240 条记忆同一天开始被管理，在第 389 天前后同时到期，限速每次清理最多 5 条（`max(5, 2%)`），到期后一个多月忘完，没有一次性发生。被忘的先存档，90 天后真正清除。
- **每题平均返回条数**：混合后端 0.77 → 0.49（默认）；关键词后端 0.42 → 0.32。这不是“更干净”，主要是库里少了东西，返回的就少。
- **噪声率**：混合后端 15.2% → 10.2%（默认）、10.6%（钉住）、8.8%（激进）；关键词后端 7.8% → 10.5%（默认）、7.0%（钉住）、10.5%（激进）。**没有一致的改善**：混合后端降了，关键词后端默认和激进反而升了；噪声率的分母（返回的条数）本身也在变。混合后端第 90 天（还没有删除）噪声就从 15.2% 降到 13.3%，那是排序的作用，不是删除的作用。
- **新旧矛盾题（updated，20 题）里新的排在旧的前面**：默认的召回步骤现在带 `newer_first`（同一次请求里分数相近的几条按新的在前排），所以混合后端的基线从第 0 天起就是 70%（加 `newer_first` 之前是 40%，那时有遗忘的组靠 `freshness` 升到 60%）；有遗忘的组第 0 天同样是 70%，`freshness` 在这个指标上没有再多出什么。关键词后端没有变化（15%：它很少把一个题的新旧两条一起交出来）。到第 540 天混合后端掉到 40%（默认、激进）和 45%（钉住身份类），低于基线的 70%；关键词后端 10%（默认、激进）和 15%（钉住身份类），基线 15%。原因是这 20 题里有一批新旧两条都已经被删。**这个指标在删除之后不再说明排序，说明的是库里还剩什么。** 这一版和加 `newer_first` 之前的一次相比，只有这一列变了，Hit@5、条数、噪声率、库内条数、被删条数都完全相同。

### 付出了什么

1. **冷题命中率清零或接近清零**：混合后端 62.5% → 0.0%（默认）、15.0%（钉住身份类）、0.0%（激进）；关键词后端 30.0% → 0.0%、10.0%、0.0%。这是设计目标，也是代价：从来没人问的事几乎全被忘了（默认组冷题的期望记忆被删了 35 条，两个后端都是），只有存档期（90 天）内用 `forget restore` 取得回，过了就没有了。
2. **钉住身份类只保住了一部分**：39 条身份类（16%）钉住后，冷题命中率是 15.0%（混合）和 10.0%（关键词），库里比默认组多留了 28 到 31 条。没有钉住的其余记忆（事件、偏好、计划、实体）照样被忘。
3. **热题、温题的期望记忆也有被删的**：混合后端默认组热 9 条、温 12 条（关键词后端热 15、温 24）。热题 Hit@5 没有因此降低，因为这些题的期望记忆要么本来就没被默认阈值检索出来（基线热题命中只有 70% 和 55%），要么还有别的记忆能答；检索越弱（关键词后端）被删得越多，这就是“遗忘放大检索盲区”。
4. 个别组热题或温题的 Hit@5 比基线低 2.5 个百分点（见上）。

### 没有测到的

- 真实的使用记录：这里的流量是按固定分布抽的。
- 记忆陆续写入的库：这里 240 条同一天装进来、同一天开始被管理，到期也在同一天；真实的库里到期是错开的，限速几乎不会起作用。
- 多个存储、按来源分别设半衰期。
- 客户端回报（`POST /v1/used`）和 `credit = "all"` 的对照：模拟里只有默认的 `credit = "top"`，没有单独测每一项改动的贡献。
- 客户端真的把记忆放进提示词才算“用到”：这里是“召回并且相似度最高（或几乎一样高）”就算。
- 参数是起点：默认值没有在真实数据上调过，这个模拟也不是调参的依据。

### 怎么重新生成

关键词后端（几十秒，不联网）：

    python bench/forgetting_sim.py --backend sqlite --out bench/results/forgetting

混合后端需要 embeddings 接口，在容器里跑（约 3 分钟；`bench/run_all.sh` 里有现成的命令）：

    docker run --rm --network fmg-bench -v <仓库>:/repo:ro -v <仓库>/bench/results/forgetting:/repo/bench/results/forgetting -w /repo -e PYTHONPATH=/repo/src -e PYTHONUTF8=1 python:3.12-slim python bench/forgetting_sim.py --backend hybrid --embed-url http://fmg-bench-embedder:11434/v1 --out bench/results/forgetting

每次运行会重写 `summary.md`（把已有的两个后端的结果合在一起，并附上这份 `reading.md`）；只想重新合并、不重跑：`python bench/forgetting_sim.py --combine-only`。
