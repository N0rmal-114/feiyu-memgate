# 聊天场景的测试题

`bench/data` 和 `bench/dev` 里的题目都是提问：“主人的猫叫什么”。聊天里更常见的是另外两种情况，那两套题量不出来：

- **闲聊**。主人说“最近天气有点热”，没有在问什么。一个了解他的朋友会想起“他很怕热”“他喜欢吃冰淇淋”，再顺着想起“上次他的冰淇淋掉在了地上”。这里要找的记忆和这句话没有相同的词，有的还要经过另一条记忆才连得上。
- **追问**。前面几轮已经在聊一件事，主人接着说“那后来呢”“它多少钱来着”。单看这一句不知道在问什么。

这一套题专门量这两种情况，外加“该安静的时候是不是安静”。

## 数据是怎么造的

每个“世界”是一个虚构的人和关于他的 60 条记忆，记忆是按“簇”写的，这样标注有据可查，不靠感觉：

- 一个**簇**围绕一个具体的东西：一只宠物、一种吃的、一个人、一个地方、一件电器、一个习惯。每个簇有一条**事实**（“主人喜欢吃冰淇淋，最喜欢香草味的”）和一到三条**经历**（“主人上次在公园吃冰淇淋的时候，冰淇淋掉在了地上”）。经历里一定出现这个簇的名字或别名，别名由事实那一条引入（事实说“主人养了一只橘猫，名字叫年糕”，经历可以只说“年糕”）。
- 另有一些不属于任何簇的**零散**记忆，作为干扰。

题目分四类：

| 类型 | 是什么 | 标注 |
|---|---|---|
| `remark-assoc` | 一句闲聊，不出现簇的名字，但按日常的常识会让人想到它 | `direct`：这个簇的事实；`chain`：这个簇的经历 |
| `remark-named` | 一句闲聊，直接提到了簇的名字或别名 | `direct`：这个簇里的全部记忆 |
| `follow-up` | 两到四轮对话之后的一句短话，单看这一句不知道指什么 | `direct`：能接上这句话的那一两条记忆 |
| `quiet` | 一句和所有记忆都无关的闲聊 | 都为空：什么都不交才对 |

每道题另有 `also_ok`：不在标注里、但交出来也说得过去的记忆，不算杂讯。`why` 用一句话写明联想的理由（“热，想吃冷的”）。

后来加的世界里，`remark-assoc` 还带一个 `kind`，写明这句闲聊是靠什么让人想到那条记忆的，每个世界每类两道：

| `kind` | 这句话是 | 该想到的是 | 例子 |
|---|---|---|---|
| `craving` | 想吃、想喝、想要 | 他惯常吃的东西、常去的地方 | “热得想喝点凉的甜的” → 他爱去的糖水铺 |
| `body` | 身体上的感觉或不舒服 | 已知的原因、老毛病、他用的办法 | “改完作业脖子好酸” → 他买的按摩仪 |
| `trigger` | 外面的事：天气、声音、要办的事、看到的东西 | 他有的东西、常做的事、常去的地方 | “雨好大，没带雨衣” → 他上下班骑的电动车 |
| `time` | 时间：某个日子快到了、季节、钟点、年纪 | 一件定期的事 | “下个月就三十三了” → 妈妈张罗的相亲 |
| `trait` | 眼前要遇到的一个场合 | 他的一个特点、忌口、过敏、害怕的东西 | “同事约了海鲜自助” → 他对虾过敏 |
| `emotion` | 一种心情或气氛 | 他生活里的一个人或一只宠物 | “一个人在家有点冷清” → 他养的仓鼠 |

最早的四个世界没有 `kind`。后来的世界还有两处不同：每个世界至少五道联想题和目标那条事实没有相同的字词，只靠常识连得上；每三个簇里有一个簇的事实不是这个簇里最早的一条（真实的记忆库里，事实不一定最先写下）。

## 多轮会话

单句题量不出一件事：话一路聊下去，晚了一轮才找到的记忆还有没有用，话题一换，带上的无关记忆有多少，第二天开一场新对话，能不能接上昨天的话题。所以世界可以另带一个可选的列表 `sessions`（没有这个键的世界照样合格）。一个世界有三场会话，每场 6 到 9 轮：

```json
{"id": "s01", "turns": [
  {"kind": "open", "user": "最近天气有点热", "assistant": "是啊，这几天热得人没精神。", "cluster": "c01", "direct": ["m001"], "also_ok": []},
  {"kind": "continue", "user": "上回那次真是可惜", "assistant": "哪一次呀？", "cluster": "c01", "direct": ["m002"], "also_ok": []},
  {"kind": "idle", "user": "楼下又在修路了", "assistant": "修路是挺吵的。", "cluster": null, "direct": [], "also_ok": []},
  {"kind": "named", "user": "年糕今天又挠沙发了", "assistant": "它又调皮了。", "cluster": "c02", "direct": ["m003"], "also_ok": []},
  {"kind": "return", "user": "对了，刚才说到吃的那个，我想好了", "assistant": "想好什么了？", "cluster": "c01", "direct": ["m001"], "also_ok": []},
  {"kind": "nextday", "new_conversation": true, "gap_days": 1, "user": "昨天说的那个还是没买成", "cluster": "c01", "direct": ["m001"], "also_ok": []}
]}
```

一轮的字段：`kind` 是下面六种之一；`user` 是主人说的话（1 到 30 个字）；`assistant` 是这一轮里陪伴者的回话，后面几轮的历史里就用它（1 到 50 个字），除了一场会话的最后一轮可以不写，其余每轮都要有。它只是一句中性的回应或一个问题，测试不看它的内容，只查下面的规则；`cluster` 是这一轮在聊的簇，没有就是 `null`；`direct` 是这一轮该摆到模型面前的记忆，`also_ok` 是交出来也说得过去的别的记忆，这个簇的其余记忆打分时都算相关，不用列。`new_conversation: true` 加整数 `gap_days`（至少 1）表示这一轮是隔了这么多天之后的一场新对话，之前的历史没有了。

| `kind` | 主人这句话 | 要求 |
|---|---|---|
| `open` | 靠联想开起一个话题，像 `remark-assoc` | `direct` 恰好是这个簇的事实；这句话不出现簇的名字 |
| `named` | 点名开起或换到一个话题 | `direct` 不空，且全属于这个簇；这句话出现簇的某个名字 |
| `continue` | 接着上一轮的话题往下说，不点名 | 上一轮就是同一个簇（中间不能隔着闲聊）；`direct` 是这个簇的 1 到 2 条；不出现簇的名字 |
| `idle` | 和任何记忆都无关的闲聊 | `cluster` 为 `null`，`direct` 和 `also_ok` 都空 |
| `return` | 回到同一场对话里早先离开过的话题，不点名 | 这个簇在本场对话里出现过，而且紧挨着的上一轮不是它；`direct` 1 到 2 条；不出现簇的名字 |
| `nextday` | 新对话的第一句，不点名地提起前一场对话里的话题 | 必须带 `new_conversation` 和 `gap_days`；这个簇在前一场对话里出现过；`direct` 1 到 2 条；不出现簇的名字 |

一场会话的规则，用大白话说：第一轮是 `open` 或 `named`；`open`、`continue`、`idle`、`return` 各至少一轮，`nextday` 恰好一轮；至少涉及两个不同的簇；只有 `nextday` 那一轮开新对话，也只有它能开；`nextday` 之后最多再有两轮，只能是 `continue`、`idle`、`named` 或 `open`；会话 id 写成 `s01`、`s02`……，在世界里不重复；记忆 id 都要存在，同一条记忆不能同时在 `direct` 和 `also_ok` 里。陪伴者的回话不能含有它这一轮的簇、或之后任何一轮的簇的名字：写好的回话不能把话题的名字递给后面的检索。一个世界有三场会话，同一个簇不能出现在两场会话里。

怎么量：每一轮单独算。看的是这一轮的 `direct` 记忆有没有在模型面前，不管是这一轮才交出来的，还是之前几轮交过、现在还留在这场对话的历史里（新对话里历史清空，只算这一轮自己交的）；另外数这一轮新交出来的记忆里有多少和这一轮无关。这样“晚一轮才找到”和“换话题后带了多少旧东西”都能从数字里看出来。

写会话用 `sessions_tool.py`：`show` 把一个世界的人设、每个簇（键、名字、别名、各条记忆）和零散记忆打印出来，不打印这个世界的题目，也不打印已有的会话，免得照抄；`set` 把一个含三场会话的 JSON 列表写进世界文件的 `sessions`（已有的会被换掉，键放在最后，文件格式不变），然后跑一遍检查，有问题就打印并以 1 退出（文件照样写好，改完再跑一次即可）。

```bash
python -B bench/chat/sessions_tool.py show bench/chat/dev/dev-teacher.json
python -B bench/chat/sessions_tool.py set bench/chat/dev/dev-teacher.json sessions.json
```

## 文件

```text
bench/chat/
  validate.py          检查一个世界文件是否符合上面的规则
  sessions_tool.py     写多轮会话用的小工具：show 看世界，set 写入并检查
  replies/             回复质量的评估：脚本和两份任务单（见下面“回复质量”）
  dev/<世界>.json      开发集：选规则、调参数只看这里
  test/                测试集：冻结，不看着它调任何东西；不在仓库里
```

每个划分 12 个世界：720 条记忆，144 道联想闲聊、72 道指名闲聊、96 道追问、48 道该安静的闲聊，一道联想题占 0.7 个百分点。最早是每个划分 4 个世界；[docs/design/2026-11-18-linked-recall.md](../../docs/design/2026-11-18-linked-recall.md) 里“试过什么”的数字是在那 4 个世界上量的，扩大之后的数字在同一篇的最后一节。新世界是用语言模型按同一份出题说明分头独立写成的（互相看不到对方的内容），再由另一轮独立的复查逐题核对标注，最后把不同世界里重复的内容（同一种过敏、同一个名字、同一句该安静的话）换掉。

一个世界文件：

```json
{
  "world": "dev-teacher",
  "persona": "一句话说明这个人是谁",
  "clusters": {"c01": {"entity": "冰淇淋", "terms": ["冰淇淋"]}},
  "memories": {
    "m001": {"text": "主人喜欢吃冰淇淋，最喜欢香草味的", "date": "2026-06-02", "cluster": "c01", "role": "fact"},
    "m002": {"text": "主人上次在公园吃冰淇淋的时候，冰淇淋掉在了地上", "date": "2026-08-15", "cluster": "c01", "role": "episode"},
    "m050": {"text": "主人的手机屏幕摔裂过，一直没去换", "date": "2026-08-20", "cluster": null, "role": "filler"}
  },
  "cases": [
    {"id": "r01", "type": "remark-assoc", "history": [], "message": "最近天气有点热",
     "direct": ["m001"], "chain": ["m002"], "also_ok": [], "why": "热，想吃冷的"}
  ]
}
```

`history` 是这句话之前的对话，每项是 `{"role": "user" 或 "assistant", "content": "..."}`；只有 `follow-up` 需要。

检查：

```bash
python -B bench/chat/validate.py bench/chat/dev
```

## 怎么量

`run.py` 通过真实的网关（进程内）把一个划分跑一遍，按题型给出：闲聊里直接相关的那条有没有交出来（`direct`）、相连的记忆交出来多少（`chain`）、交出去的条目里相关的占多少、每句话交几条、追问命中、该安静的时候是不是安静。指标的定义在它的文档字符串里。

```bash
python -B bench/chat/run.py --split bench/chat/dev --backend sqlite --table
python -B bench/chat/run.py --split bench/chat/dev --backend hybrid --url <embeddings 接口> --model bge-m3 --linked off --table
```

`--linked off` 是去掉 `linked` 步骤的默认管线，用来和现在的默认（`on`）比。`methods.py`、`sweep.py`、`vector_lab.py`、`model_lab.py`、`session_lab.py` 是实验用的：把一种改法做成可以对比的变体，在开发集上扫参数。它们不是产品代码。`model_lab.py` 比的是要靠语言模型的做法，模型写的文字作为文件交给它，它自己不调用模型。`session_lab.py` 按轮回放 `sessions`，量的是一段对话里的事：晚一轮才到的记忆、历史被压缩、隔天新开对话。`noise.py` 是这两个脚本共用的几种过滤规则（只从结果里往下拿记忆）。已经量过的做法和结果见 [docs/design/2026-11-18-linked-recall.md](../../docs/design/2026-11-18-linked-recall.md) 、[docs/design/2026-11-18-recall-with-a-model.md](../../docs/design/2026-11-18-recall-with-a-model.md) 、[docs/design/2026-11-18-sessions.md](../../docs/design/2026-11-18-sessions.md) 和 [docs/design/2026-11-21-noise.md](../../docs/design/2026-11-21-noise.md)。

## 回复质量

`replies/` 量的是上面那些指标量不到的一件事：同一轮对话里，换一种给记忆的办法之后，回复有没有变好。`in_front` 只说记忆摆到了模型面前，`mentions` 只说回复和记忆有相同的词。这里让写回复的模型和评判的模型各读一份任务单，一份输入文件，写一个 JSON，脚本只负责切文件、合并和打分，不调用任何模型。流程六步：

1. `plan.py` 按配置（`base`、`after`、`recent`、`cap3`、`strict`、`combo`、`combo-strict`，外加把 `base` 再写一遍的 `aa`）回放开发集的会话，用缓存的向量和已有的回复文本，不需要向量服务；每一轮得到一份交给写回复一方的材料（人设、这场对话到此为止的内容、主人的话、记忆块；和产品一样，前面几轮给过的记忆块留在对话里，挂在对应那句主人的话的 `notes` 上，新开对话则清空），记忆块的措辞由 `handover.mjs` 调插件的 `block.js` 生成；最后打印成本表（要写多少条回复、要评多少对）。
2. `prep.py write` 把还没有回复的材料切成每份 24 条的输入文件，按 `TASK-REPLY.md` 写回复。
3. `prep.py judge` 在回复合并之后，把每个配置的回复和 `base` 的回复配成对，用固定种子的硬币决定谁在 `a`、谁在 `b`，十分之一的对再以相反的顺序出现一次；按 `TASK-JUDGE.md` 评判。评判看到的历史只有话，不带记忆块；摆在写回复一方面前的记忆（这一轮的和这场对话里前面各轮的）按这一轮的标注分成三份：`relevant`（直接相关的和也说得过去的，不管给没给）、`related_given`（同一个簇的、给过的）、`other_given`（不相干的、给过的）；几个配置共用的一对取它们的并集。
4. `merge.py` 合并输出，列出缺的、多的、长度不合规的回复和读不懂的评判，这些要重做，不会替它们猜。
5. `score.py` 对每个配置给出胜、负、持平和精确的符号检验，以及用到相关记忆（`u`）、提到不相干的东西（`d`）、说错或编造（`w`）的比例，按轮的类型分开；除了逐轮的符号检验，还有按会话的符号检验（同一场会话的各轮不独立，每场会话先算胜负净值，再对净值不为零的会话做检验），后者更严，报告里两个都给；`u` 的分母是 `relevant` 或 `related_given` 非空的轮，同时给出只算有 `direct` 记忆的轮的旧口径；`aa` 给出噪声的底线，交换顺序的重复给出评判是否前后一致、是否偏向 `a`。
6. 输出都在仓库之外的工作目录里（`--work`），评判不看配置名。

它能说明什么、不能说明什么：写回复和评判的都是同一系列的小模型，换一个模型可能不同；会话是照剧本写好的，主人的话不会因为回复变好或变差而改变；标注（记忆的相关与否）和会话是语言模型写成的，另由一轮独立的复查核对过，不是真人标的。所以结果是同一套条件下配置之间的比较，不是真实用户满意度。默认只在开发集上跑，测试集要加 `--final`，按“规则”一节的约定只跑一次。

在开发集上跑出的结果和对这把尺子可靠程度的估计见 [docs/design/2026-11-22-reply-quality.md](../../docs/design/2026-11-22-reply-quality.md)。

## 规则

和 `bench/dev`、`bench/data` 一样：规则和参数只在开发集上选，选定之后才在测试集上跑一次，跑完不再改。数据全部虚构。
